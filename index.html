Why RAG

為什麼需要 RAG？

一般 LLM 主要依靠訓練時學到的資訊；遇到近期資訊或組織內部資料時，可能沒有足夠依據。

只問一般 LLM

固定教材的限制

  • 可能不知道訓練資料之後的資訊
  • 不一定掌握組織的專門資料
  • 回答未必有指定資料作依據
加入 RAG

回答前先查資料

  • 取得較新的外部內容
  • 使用當前任務需要的資料
  • 讓回答以相關內容作為參考
教學示例（非來源事實）

詢問「今年有幾天家庭照顧假？」時，先查最新版公司規章，再交給模型整理回答。

重要界線：RAG 增加可參考的依據，並不保證答案一定正確。

Definition

RAG 是什麼？

檢索增強生成把資訊檢索系統與生成式 LLM 結合：先找出相關外部內容，再讓模型把內容當作回答依據。

Retrieval從外部來源找出相關內容
Pre-processing整理成模型可使用的脈絡
Grounded Generation依據取得的內容產生回答

RAG 多做了一件事

模型回答前，系統先取得與問題相關的外部資料。

RAG 沒有承諾的事

「有檢索」不等於「一定找對」，也不等於生成答案必然正確。

Architecture

RAG 的完整流程

先在離線階段準備可搜尋的索引；使用者提問後，再於線上階段檢索、加入脈絡並生成回答。

離線：先準備
文件處理整理與切分
Embedding轉成向量表示
建立索引保存文字、向量與 metadata
線上：每次提問
Query接收問題
Retrieve找出相關片段
Augment把片段加入脈絡
Generate模型產生回答
一句話記法

先把資料整理成「找得到」的形式；提問時，再把「找對的資料」交給模型。

Step 1 · Chunking

把大文件切成可處理的片段

Chunking 通常位於索引準備階段、建立 Embedding 之前，讓文件能被分段處理與檢索。

固定長度

依字元或 token 數切分，規則簡單，但可能切斷語意。

依結構

依句子、段落或標題切分，較能保留文件組織。

依語意

以內容語意變化決定邊界，成本與複雜度較高。

組合策略

把結構、大小與其他條件一起使用。

較小 Chunk
比較聚焦，可能失去前後關係
較大 Chunk
保留更多脈絡，可能混合多個主題
教學示例（非來源事實）

員工手冊可先依章節切分，再讓相鄰片段保留少量重疊，避免一句規則被切在邊界兩側。

沒有脫離資料與任務的單一最佳 Chunk Size；Overlap 也不是越大越好。

Wiki03〈常見切分策略〉、〈Chunk Overlap〉、〈如何選擇 Chunk Size？〉Source IDs：S02、S03

Step 2 · Embedding

把文字轉成可比較的向量

Embedding 是文字的數值表示，用來表達內容的語意或脈絡；文件片段和問題都可轉成相容的表示。

意思變成「座標」

向量距離可用來衡量文字的相關程度；距離較小通常代表較相關。

Embedding ≠ Vector Database

Embedding 是表示；Vector Database／索引負責保存並支援搜尋。

視覺化為教學示意

圖中的位置與距離不是實際運算結果，只用來幫助理解「語意相近的文字可被排得較近」。

Wiki04〈Embedding 是什麼？〉、〈Embedding 與 Vector Database 不一樣〉、〈S04 補充〉Source IDs：S02、S04

Step 3 · Retrieval

先找出最相關的資料

Retriever 不直接回答問題；它的任務是從外部資料中選出可能有用的候選片段。

向量搜尋

依語意相似度尋找與 Query 接近的內容，不只比對完全相同的字詞。

Hybrid Search

結合關鍵字與向量搜尋，使用兩類不同的比對線索。

Reranking

取得候選內容後再評分，讓較相關的結果排在前面。

Query使用者問題
Candidate Set找出候選片段
Optional Rerank重新評估順序
Context交給模型的內容

Hybrid Search 與 Reranking 是可選的進階做法；Embedding 本身也不等於完整 Retriever，更不保證第一名結果能回答問題。

Wiki05〈向量搜尋〉、〈Hybrid Search〉、〈Reranking〉、S04/S05 補充Source IDs：S01、S04、S05

Step 4 · Generation

讓模型依據找到的內容回答

系統把使用者問題與檢索到的 Context 一起交給 LLM，模型再利用額外脈絡產生回答。

Query「家庭照顧假有幾天？」
Retrieved Context相關規章片段
LLM結合問題與脈絡
Answer依據片段組織回答

Grounding 的價值

回答能以指定的外部內容為參考，而非完全依靠訓練時學到的資訊。

仍然需要檢查

如果取回的內容不相關，即使模型依據它回答，結果仍可能離題或錯誤。

本頁只說明 Wiki 支持的基礎 Generation 角色，不延伸到 Prompt 模板或生成參數。

Quality Check

有資料依據，仍不等於一定正確

RAG 品質同時受到知識來源、檢索相關性與生成結果影響。初學者可以先用五個問題檢查。

  1. 系統有找到資料嗎？
  2. 找到的內容真的相關嗎？
  3. 回答有依據取得的內容嗎？
  4. 資料夠新嗎？
  5. 回答真的解決問題嗎？

常見限制

查詢意圖、多來源資料、模型輸入限制、回應時間，以及安全與權限，都可能影響實作結果。

進階但通用的原則

可用明確規則檢查回答是否以證據為依據；若需修訂，應設定次數上限並保留可追查紀錄。

Hybrid Search、Reranking 或特定追蹤產品都不能單獨保證答案正確。

理解測驗｜點選題目看答案

1. 為什麼 RAG 能使用較新的資料？

因為系統可在回答時取得外部內容，而不只依賴 LLM 訓練時學到的資訊。（Wiki 01、06｜S01）

2. Chunking 為什麼不能只套用一個固定大小？

Chunk 大小要配合文件結構、查詢方式、模型限制與使用情境；大小兩端各有取捨。（Wiki 03｜S03）

3. Grounding 是否代表答案一定正確？

不是。若檢索內容不相關，依據那些內容生成的回答仍可能離題或錯誤。（Wiki 01、05、06｜S01）

最後一句：RAG 不是讓模型知道所有事情，而是讓系統在回答前，先取得更適合的外部依據。
